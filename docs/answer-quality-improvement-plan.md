> 작성일: 2026-03-09 | 상태: 기획안 (구현 전)

## 1. 원인 분석 (파이프라인 단계별)

| 단계 | 파일/함수 | 문제 | 심각도 |
|------|-----------|------|--------|
| **① 질문 분류** | `question_filter.py` → `detect_category` | 5개 카테고리(career/projects/collaboration/process/decision)로만 분류. 질문 의도의 깊이·맥락 구분 없음 | 🟡 중 |
| **② 답변 구조 강제** | `llm_service.py` → `build_user_payload` | **모든** 질문에 동일한 마크다운 구조(핵심요약/사례PAR/채용관점) 강제 | 🔴 핵심 |
| **③ 하드코딩 폴백** | `llm_service.py` → `_build_rag_fallback_answer` | 3가지 if/elif/else 분기로 **고정 문장**을 반환. 협업→고정문장A, 우선순위→고정문장B, 나머지→고정문장C | 🔴 핵심 |
| **④ 과도한 폴백 트리거** | `_is_low_quality_answer` + quality모드 | quality 모드에서 LLM 답변을 무시하고 항상 하드코딩 폴백 사용. 저품질 판정 기준도 너무 느슨 | 🔴 핵심 |
| **⑤ RAG 검색** | `knowledge_base.py` → `_retrieve_lexical_chunks` | 토큰 빈도 기반 cosine만 사용. 프로젝트/포트폴리오 가산점이 고정값이라 질문별 근거 차별화 약함 | 🟡 중 |
| **⑥ 시스템 프롬프트** | `system_prompt.txt` | 프롬프트 자체는 양호하나, user payload의 구조 강제와 결합되면 LLM이 틀을 벗어나지 못함 | 🟢 낮 |

### 핵심 결론
> **반복의 80%는 ③ 하드코딩 폴백 + ② 구조 강제가 원인.** LLM이 다양하게 생성해도, 폴백으로 빠지거나 동일 구조가 강제되면서 '템플릿 복붙'이 됨.

## 2. 개선 전략 3단계

### Phase 1: 빠른 핫픽스 (1~2일)

| # | 작업 | 효과 |
|---|------|------|
| 1-1 | `_build_rag_fallback_answer` 하드코딩 문장 제거 → RAG 청크 기반 **동적 조립**으로 교체 | 고정 문장 반복 즉시 해소 |
| 1-2 | `build_user_payload`의 구조 강제를 **카테고리별 분기**로 변경 (아래 §3 스키마 참조) | 질문 유형별 답변 형태 차별화 |
| 1-3 | `quality` 모드에서 LLM 답변 무시 로직 제거 → LLM 우선, 폴백은 최후 수단으로 | LLM 생성 다양성 확보 |
| 1-4 | `_is_low_quality_answer` 판정에 **질문-답변 키워드 매칭** 추가 (질문 핵심어가 답에 없으면 저품질) | 질문과 동떨어진 답변만 재생성 |

### Phase 2: 구조 개편 (3~5일)

| # | 작업 | 효과 |
|---|------|------|
| 2-1 | 질문 의도 분류를 LLM 기반 **intent classifier**로 교체 (현재 키워드 매칭 → 소형 모델 분류) | 질문 뉘앙스 구분 (예: "협업 갈등" vs "협업 방식") |
| 2-2 | 답변 스키마를 의도별로 분리 (§3 참조). 시스템 프롬프트에 의도별 가이드 주입 | 구조 자체가 달라져 체감 차이 큼 |
| 2-3 | RAG에 **의도-청크 매핑 메타데이터** 추가 (각 청크에 `intent_tags` 필드) | 관련 없는 청크 노출 감소 |
| 2-4 | 세션 내 이전 답변 요약을 context에 포함 → **"직전 답변과 겹치지 않게"** 지시 | 같은 세션 내 반복 방지 |

### Phase 3: 고도화 (1~2주)

| # | 작업 | 효과 |
|---|------|------|
| 3-1 | pgvector 벡터 검색 활성화 + 하이브리드 가중치 자동 튜닝 | 근거 정밀도 향상 |
| 3-2 | 답변 품질 자동 평가 파이프라인 (§6 지표 기반) | 지속적 품질 모니터링 |
| 3-3 | 답변 캐시 + 유사 질문 감지 → 캐시 hit 시 변형 생성 | 동일 질문 반복 방문 시에도 신선한 답변 |
| 3-4 | A/B 테스트 프레임워크 (답변 variant별 만족도 추적) | 데이터 기반 개선 루프 |

## 3. 질문 의도별 답변 스키마 제안

### 🤝 협업 (collaboration)
```
## 협업 스타일
(309의 협업 접근법을 1~2문장으로)

## 구체적 상황
(실제 프로젝트에서 팀/이해관계자와 어떻게 일했는지. PAR 중 P-A 중심)

## 결과와 교훈
(정량/정성 결과 + 본인이 배운 원칙)
```
**핵심:** "채용관점 기대효과" 섹션 없음. 협업 질문은 경험 중심이지 채용 포장이 아님.

### 🎯 우선순위 / 의사결정 (process, decision)
```
## 판단 프레임워크
(우선순위를 어떤 기준으로 세우는지. 2~3가지 원칙)

## 적용 사례
(프로젝트명 + 실제로 어떤 선택을 했고 왜)

## 트레이드오프
(포기한 것과 그 이유)
```
**핵심:** "트레이드오프"를 명시해 깊이감 확보. 일반적 답변과 차별화.

### 💎 채용 강점 / 경력 (career)
```
## 핵심 강점
(3가지 이내, 각 1문장)

## 근거 사례
(각 강점별 프로젝트 기반 증거)

## 팀에 기대할 수 있는 것
(채용관점에서 이 사람이 들어오면 뭐가 바뀌는지)
```
**핵심:** 채용 질문에서**만** 채용 관점 섹션 사용. 다른 질문에서는 쓰지 않음.

### 🔍 문제정의 / 프로젝트 (projects)
```
## 맥락
(프로젝트 배경 1~2문장)

## 문제 정의 과정
(어떻게 진짜 문제를 찾았는지. 분석 방법/유저 리서치/데이터)

## 해결과 결과
(무엇을 만들었고 어떤 변화가 있었는지)
```
**핵심:** "핵심요약" 같은 추상 헤더 대신 프로젝트 서사 중심 구조.

## 4. 중복 방지 로직 제안

### 4-1. 세션 내 중복 감지
```python
# 의사코드
previous_answers = get_session_answers(session_id)
for prev in previous_answers:
    sim = cosine_similarity(new_answer_embedding, prev.embedding)
    if sim > 0.82:  # 임계값
        regenerate(extra_instruction="직전 답변과 표현/구조/사례를 바꿔서 작성")
```
- **기준:** 답변 임베딩 코사인 유사도 > 0.82 → 재생성
- **최대 재생성:** 2회 (무한루프 방지)

### 4-2. 문장 단위 반복 감지
- 답변 내 문장을 추출해 이전 답변 문장과 편집거리 비교
- **동일 문장 2개 이상** 발견 시 해당 문장만 LLM에게 재작성 요청 (전체 재생성보다 효율적)

### 4-3. 하드코딩 금지 원칙
- `_build_rag_fallback_answer` 내 **모든 고정 문자열 제거**
- 폴백 시에도 RAG 청크 텍스트를 직접 인용 + LLM으로 재구성
- 고정 문장이 필요한 경우 최소 5개 이상의 변형 풀에서 랜덤 선택

## 5. RAG 근거 선택 기준 강화안

| 현재 | 개선 |
|------|------|
| 토큰 빈도 cosine만 사용 | **하이브리드:** 벡터 유사도(0.6) + 렉시컬(0.3) + 메타 가산(0.1) |
| 프로젝트 청크 일률 +0.12 가산 | 의도별 가산: 협업→collaboration 태그 청크 우선, 프로젝트→project 태그 우선 |
| 가드레일 청크 -0.15 감점만 | 가드레일/시스템 청크 **완전 제외** (검색 후보 자체에서 빼기) |
| top_k=6 고정 | 의도별 top_k 조정: 사례 질문은 top_k=3 (깊이), 개괄 질문은 top_k=6 (넓이) |
| 청크 최대 700자 | 핵심 청크는 전문 사용, 보조 청크만 축약 (답변 구체성 향상) |

### 추가 제안
- 각 RAG 청크에 `intent_tags: ["collaboration", "project", "career"]` 메타데이터 추가
- 검색 시 질문 의도와 일치하는 태그 청크에 **1.3x 부스트**
- 검색 결과에 `source_type: "guardrail"` 청크가 섞이면 필터링

## 6. 품질 측정 지표

| 지표 | 측정 방법 | 목표값 | 비고 |
|------|----------|--------|------|
| **문장 반복률** | 최근 20개 답변 중 동일 문장(편집거리<5) 비율 | < 10% | 현재 체감 50%+ |
| **구조 반복률** | 동일 헤더 조합(예: 핵심요약+PAR+채용관점) 사용 비율 | < 40% | 현재 ~95% |
| **근거 일치율** | 답변 내 사례가 RAG 청크에 실제 존재하는 비율 | > 90% | 할루시네이션 방지 |
| **질문 키워드 포함율** | 질문의 핵심 키워드가 답변에 등장하는 비율 | > 80% | 질문 무시 방지 |
| **실무감 점수** | (프로젝트명 언급 + 구체적 수치/도구명 포함 여부) / 2 | > 0.6 | 추상적 답변 방지 |
| **폴백 비율** | 하드코딩 폴백으로 빠지는 비율 | < 15% | 현재 quality모드 100% |
| **평균 답변 길이 분산** | 답변 글자수 표준편차 | > 80자 | 길이까지 균일하면 템플릿 느낌 |

### 측정 자동화
- Firestore `conversations` 컬렉션에 `quality_metrics` 필드 추가
- 답변 생성 시 위 지표를 계산해 함께 저장
- 대시보드에 품질 트렌드 차트 추가
