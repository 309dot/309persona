## 1. 목표 / 문제 정의

| 항목 | 현재 상태 | 목표 |
|------|-----------|------|
| **답변 가독성** | `FormattedAnswer`가 `###`, `-`, `**`만 파싱. `#`/`##`, 번호 리스트(`1.`), 줄바꿈 미지원 → 답변이 한 덩어리로 보임 | 헤드라인·번호 리스트·구분선 등 풍부한 텍스트 레이아웃 |
| **프로필 입력 타이밍** | 첫 답변 후 `setTimeout 300ms`로 `VisitorInfoModal` 강제 팝업 → 답변 읽기 흐름 단절 | 비침습적(non-intrusive) 방식으로 자연스럽게 프로필 수집 |
| **프로필 모달 문구** | "회사/이름 업데이트" — 사무적, 309 페르소나 톤과 불일치 | 309 커피챗 분위기에 맞는 친근한 문구 |
| **프로필 자동 유추** | `inferVisitorProfile()` 존재하나 한국어 정규식 한정, 이름/소속만 추출 | 질문 맥락에서 역할·목적까지 유추하여 프로필 자동 보강 |

## 2. UX 원칙

1. **대화 흐름 우선** — 답변 읽기를 방해하지 않는다
2. **점진적 노출(Progressive Disclosure)** — 정보 입력은 필요한 시점에, 최소 단위로
3. **309 톤 일관성** — 모든 UI 텍스트가 "커피챗 호스트 309"의 말투
4. **옵트인 > 강제** — 사용자가 거절해도 핵심 기능은 동작
5. **가독성은 콘텐츠의 신뢰도** — 잘 정리된 답변 = 전문성 인상

## 3. 요구사항별 제안안

### 3-1. 답변 텍스트 레이아웃 개선

**현황 분석:**
- `parseAnswerBlocks()`가 `###`(heading), `-`(unordered list), 일반 문단만 처리
- `#`, `##` 헤더, `1. 2. 3.` 번호 리스트, `---` 구분선, 이모지 블록 미지원
- `renderInlineNodes()`는 `**bold**`만 처리, `*italic*`·링크 미지원

#### A안: `parseAnswerBlocks()` 확장 (자체 파서 고도화)
- `#`, `##`, `###` 3단계 헤드라인 지원
- `1.` `2.` 번호 리스트 파싱 (`<ol>`)
- `---` 수평 구분선 → `<hr>`
- `> ` 인용 블록 → 강조 박스
- **장점:** 번들 크기 제로 증가, 기존 스타일 시스템 완전 통제
- **단점:** 마크다운 엣지케이스(중첩 리스트 등) 직접 대응 필요

#### B안: `react-markdown` + `remark-gfm` 도입
- 마크다운 전체 스펙 지원 (테이블, 코드블록, 체크리스트 등)
- Tailwind Typography (`@tailwindcss/typography`) 플러그인 연동
- **장점:** 미래 확장 무제한, LLM 응답 포맷 자유도 극대화
- **단점:** 번들 +~40KB (gzipped ~12KB), 스타일 오버라이드 필요

#### ✅ 추천: A안 (자체 파서 고도화)
- **이유:** 현재 답변이 `###`, `-`, `**` 위주로 구조화되어 있음. LLM 프롬프트에서 출력 포맷을 통제 가능하므로 전체 마크다운 파서 불필요. 번들 증가 없이 빠르게 적용 가능.
- **2차 고도화 시** B안으로 마이그레이션 검토.

**구현 범위:**
| 파싱 대상 | 렌더링 | 우선순위 |
|-----------|--------|----------|
| `# H1` / `## H2` / `### H3` | `text-lg font-bold` ~ `text-[15px] font-bold` 계층 스타일 | P0 |
| `1.` `2.` 번호 리스트 | `<ol className="list-decimal">` | P0 |
| `\n\n` 문단 구분 | 문단 간 `space-y-3` 유지 | P0 |
| `---` 구분선 | `<hr className="border-slate-200">` | P1 |
| `> ` 인용 | 좌측 보더 강조 블록 | P1 |
| `*italic*` | `<em>` | P2 |

### 3-2. 첫 답변 후 프로필 입력 — 강제 모달 대안

**현황 분석:**
- `PersonaChatV2Page`에서 `usedCount === 0` 첫 답변 렌더 후 `setTimeout(() => setShowVisitorInfoModal(true), 300)` → 모달 강제 오픈
- 사용자가 답변을 미처 읽기 전에 모달이 뜸 → 이탈 리스크

#### A안: 인라인 배너 (답변 하단 삽입)
- 첫 답변 아래에 접을 수 있는 배너 삽입
  - "☕ 더 정확한 답변을 드리고 싶어요. 이름과 소속을 알려주시면 맥락에 맞춰 답변을 조정할게요."
  - [이름 입력] [소속 입력] [확인] [다음에]
- 답변 스크롤 흐름 내에 자연스럽게 존재
- **장점:** 답변 읽기 흐름 유지, 전환율 저하 최소화
- **단점:** 화면 공간 소비, 무시 시 계속 노출 여부 결정 필요

#### B안: 2번째 질문 입력 시 소프트 넛지 (입력창 내 힌트)
- 첫 질문 시: 입력창 하단 "질문 먼저 시작해도 됩니다" (현재와 동일)
- 첫 답변 후: 입력창 placeholder를 "이름과 소속을 알려주시면 맞춤 답변을 드릴게요 — 또는 바로 다음 질문을 입력하세요"로 변경
- 이름 수정 버튼을 부드럽게 펄스 애니메이션
- **장점:** UI 변경 최소, 압박감 제로
- **단점:** 인지율 낮을 수 있음 (전환율 불확실)

#### C안: 에이전트 채팅 버블로 자연스럽게 요청
- 첫 답변 직후, 309 에이전트가 추가 채팅 버블로:
  - "참, 혹시 실례가 안 된다면 이름과 소속을 알려주실 수 있을까요? 맥락에 맞춰 더 정확하게 답변드릴 수 있거든요. 😊 (선택사항이에요!)"
- 버블 내에 미니 입력 폼 or "입력하기" 버튼 → 인라인 모달
- **장점:** 대화 흐름 100% 유지, 309 페르소나 톤 자연스럽게 적용
- **단점:** 구현 복잡도 약간 증가 (채팅 버블 내 인터랙션)

#### ✅ 추천: C안 (에이전트 채팅 버블)
- **이유:** 커피챗 서비스 특성상 "대화 속에서" 프로필을 요청하는 것이 가장 자연스러움. 309의 페르소나 톤을 그대로 유지하면서 정보를 수집할 수 있음. 사용자가 무시해도 대화는 계속 진행 가능.
- **폴백:** 사용자가 무시하면 2번째 답변 후 다시 요청하지 않음 (1회성)

### 3-3. 프로필 모달 문구 개선

**현황 분석:**
- `VisitorInfoModal`: "Visitor Info" / "회사/이름 업데이트" — 관리자 어투
- `VisitorModal` (ChatPage): "커피챗을 시작하기 전에" — 상대적으로 나음

#### A안: 309 페르소나 톤 적용 (캐주얼-프로페셔널)
```
제목: "잠깐, 자기소개 좀 부탁드릴게요 ☕"
본문: "이름과 소속을 알려주시면 질문 맥락에 맞춰
      더 정확한 답변을 드릴 수 있어요."
부가: "입력하신 정보는 이 대화에서만 활용돼요."
버튼: "알려줄게요" / "다음에 할게요"
```

#### B안: 미니멀 원라이너
```
제목: "누구와 이야기하고 있는지 알면 좋겠어요"
본문: (없음 — 입력 필드만)
부가: "선택사항이에요. 건너뛰셔도 됩니다."
버튼: "확인" / "건너뛰기"
```

#### ✅ 추천: A안
- **이유:** 309의 "커피챗 호스트" 페르소나와 일치. 정보 활용 목적을 명확히 전달하면서도 부담 없는 톤. B안은 너무 건조.

**적용 위치:**
- `VisitorInfoModal` (PersonaChatV2Page) — 주력
- `VisitorModal` (ChatPage) — 레거시이지만 동일 톤 통일

### 3-4. 질문 내용에서 프로필 유추

**현황 분석:**
- `inferVisitorProfile()`이 이미 존재: 이름/소속 정규식 매칭
- 한계: "저는 쿠팡 PM 홍길동입니다" 같은 명시적 자기소개만 포착
- 역할(PM/디자이너/리크루터), 목적(채용/협업/스터디) 유추 없음

#### A안: 클라이언트 키워드 매칭 확장
- 기존 `inferVisitorProfile()` 확장
- 역할 키워드: `PM`, `디자이너`, `개발자`, `리크루터`, `HR`, `CTO` 등
- 목적 키워드: `채용`, `협업`, `프로젝트`, `스터디`, `참고` 등
- 추출 결과를 `visitorRole`, `visitorPurpose` 필드로 확장
- **장점:** 지연 없음, 추가 API 호출 없음
- **단점:** 정교한 맥락 이해 불가 (키워드 의존)

#### B안: LLM 사이드 추출 (백엔드 프롬프트 확장)
- 백엔드 답변 생성 시 시스템 프롬프트에 추가:
  - "사용자 질문에서 이름, 소속, 역할, 목적을 추론할 수 있으면 JSON으로 함께 반환하라"
- 응답 JSON에 `inferred_profile` 필드 추가
- 프론트엔드가 이를 받아 프로필 자동 업데이트 (사용자 확인 후)
- **장점:** 자연어 맥락 이해 가능, 정확도 높음
- **단점:** 응답 지연 약간 증가, 프롬프트 토큰 소비

#### ✅ 추천: A안 (1차) → B안 (2차 고도화)
- **이유:** 1차에서는 클라이언트 키워드 매칭으로 빠르게 역할/목적 추출. 2차에서 LLM 기반 추출로 정확도 향상.
- 두 방식 모두 **사용자에게 확인 스낵바** 표시: "혹시 [쿠팡]의 [PM]이신가요?" → [맞아요] [아니에요]
