## 01 Every Number — 숫자마다 영수증이 붙는 대시보드

- URL: https://www.309designlab.com/work/everynumber
- 기간: 2026.10 — 현재
- 역할: 창업자 · PM · 프로덕트 디자인 · AI 에이전트 운영
- 플랫폼: 웹 (영문 SaaS) · MCP 서버
- 범위: 가설 설계, 제품 기획, UX/UI, 에이전트 작업 규칙, 품질 게이트, MCP · 에이전트 API
- 결과: 263/265 AI 에이전트와 함께 쓴 커밋 (3주) / 284→703개 통과하는 자동 테스트 (10.19 → 11.04) / 26→0곳 넘침 검사 게이트로 없앤 화면 넘침 (모두 만드는 쪽의 숫자입니다. 수요는 코드보다 먼저 정해 둔 기준으로 판정일(2026.11.27)에 가립니다.)
- 산출물: 가설 카드 · 판정 스크립트, 영수증이 붙는 대시보드 웹앱, 자연어로 고치기(Ask) · 무엇이 숫자를 움직였나, 수식이 살아 있는 Excel 내보내기, MCP 서버 · 에이전트 API, 에이전트 작업 규칙 · 품질 게이트

**AI가 숫자를 쓰지 않는 대시보드를, AI 에이전트와 3주 만에 만들었습니다**

스프레드시트나 CSV를 올리면 대시보드가 되고, 숫자를 누르면 그 숫자의 정의와 계산에 쓴 행, 뺀 행과 그 이유, 원본 파일이 담긴 ‘영수증’이 열립니다. 가설 카드를 쓴 날부터 지금의 모습까지 3주가 걸렸습니다. 코드와 테스트, 배포는 AI 에이전트가 맡았고, 저는 에이전트가 혼자 정해도 되는 일과 제가 정해야 하는 일의 경계, 그리고 어떤 경우에도 지켜야 할 기준을 만들었습니다.

### Brief — 코드보다 먼저, 틀렸을 때 접을 기준을 적었습니다

매주 엑셀이나 CSV로 숫자를 뽑아 보고하는 사람들이 있습니다. PMO 리드, 비서실장, 이커머스 운영 리드, 대행사 AE처럼 데이터팀의 도움 없이 숫자를 다루는 실무자들입니다. 이들은 무엇을 봐야 할지 몰라 대시보드를 만들지 못하거나, AI가 낸 숫자를 믿지 못해 손으로 다시 계산한다는 것이 출발점의 가설이었습니다.
2026년 10월 15일, 코드를 쓰기 전에 가설 카드부터 채웠습니다. 무엇을 믿는지, 그 근거가 어디까지 추측인지, 가장 작은 버전은 무엇인지, 맞으면 무엇이 보이고 틀리면 무엇이 보일지, 언제 판정하고 틀리면 어떻게 할지까지 일곱 칸입니다.

1. 숫자마다 근거를 보여 줘 믿고 쓸 수 있는 대시보드
2. AI 에이전트에게 실행을 맡기고, 판단과 기준은 사람이 쥐는 작업 방식

### State 1. Hypothesis — 첫 커밋은 앱이 아니라 판정 스크립트였습니다

헤드라인 세 개를 나눠 걸고, 무엇으로 판정할지를 코드에 먼저 적었습니다.

가설 카드의 ‘가장 작은 버전’ 칸에는 ‘앱 아님’이라고 적었습니다. 그래서 첫 커밋은 대시보드가 아니라, 헤드라인 세 개를 나눠 거는 영어 랜딩 페이지와 대기 신청, 그리고 결과를 가르는 판정 스크립트였습니다. 세 헤드라인은 서로 다른 가치를 약속합니다.
A · 시간 — Stop rebuilding the same report every Monday.: 매주 같은 보고서를 다시 만드는 시간을 줄여 준다.
B · 무엇을 볼지 — New project, unfamiliar numbers? Get the dashboard you didn’t know you needed.: 낯선 숫자 앞에서 무엇을 봐야 할지 먼저 제안한다.
C · 신뢰 — AI dashboards where every number shows its work.: AI가 만든 대시보드라도 숫자마다 계산 과정을 보여 준다.
다음 날 사이트를 열면서 판정 기준을 대기 신청에서 결제한 파일럿으로 옮겼습니다. 스프레드시트 하나를 받아 영업일 닷새 안에 대시보드를 만들어 주는 $99 선결제 파일럿입니다. 판정일에 결제한 팀이 셋 이상이면 계속하고, 신청만 있으면 2주를 늘리고, 신청이 없으면 접습니다. 어느 헤드라인이 더 끄는지는 베타 분포에서 2만 번 뽑아 비교하도록 스크립트에 넣었고, 실험 기간에는 헤드라인 문구를 고치지 않기로 했습니다.
결정 — 판정 전에, 실제로 도는 서비스를 먼저 만든다: 에이전트는 가설 카드의 ‘앱 아님’을 근거로 더 작은 안을 세 번 권했습니다. 파일로 납품하기, 로그인 없는 비공개 링크, 눌러 보는 시안이었습니다. 저는 판정 전이라도 정식 기능을 갖춘 서비스를 미리 준비해 두기로 했고, 에이전트는 그날 저녁 핵심 흐름을 스테이징에 올렸습니다.
이유: 정적인 견본은 ‘어떻게 생겼나’는 보여 줘도 ‘무엇을 해 주나’는 보여 주지 못했습니다. 실제로 도는 흐름이 생기자 제 피드백도 ‘있나, 없나’에서 ‘어디가 불편한가’로 바뀌었습니다. 제품과 기술의 결정은 에이전트에게 맡겨도, 사업의 방향은 제가 정합니다.

화면: 디자인 1차에서 고른 B안(이메일 한 칸으로 신청)으로 연 첫 랜딩. 오른쪽 숫자를 누르면 영수증이 열립니다.

### State 2. Receipt — 숫자를 누르면 영수증이 열립니다

정의와 범위, 원본, 계산에 쓴 행과 뺀 행을 숫자마다 붙였습니다.

대시보드의 모든 숫자에는 영수증이 붙어 있습니다. 숫자를 누르면 그 숫자의 정의와 범위, 원본 파일, 계산에 쓴 행과 뺀 행, 그리고 뺀 이유가 열립니다. 다음 주에 새 파일을 올리면 같은 정의로 다시 계산하고, 무엇이 숫자를 움직였는지도 보여 줍니다.
처음에는 어떤 데이터를 넣어도 같은 화면 구성이 나왔습니다. 직접 써 보니 위젯 몇 개에 빈 곳이 많아 결과가 빈약해 보였고, 그래서 믿음이 가지 않았습니다. 에이전트는 비슷한 약속을 하는 데이터 도구 하나를 문서 710쪽, 화면 120개까지 벤치마크해 여섯 가지를 가져왔습니다. 자연어로 대시보드를 고치는 Ask, 팀이 확정한 정의, 나눠 보기, 살아 있는 예시가 그때 들어왔습니다. 첫 화면은 이 파일이 무엇을 말하는지부터 보여 주는 ‘Pulse board’로 바꿨습니다.

화면: 발견의 영수증 열기 → 환불률을 움직인 것 보기 → 내보내기 메뉴, 주간 KPI, 대행사 광고 리포트, 프로젝트 포트폴리오

### State 3. Boundary — AI는 숫자를 쓰지 않습니다

AI는 목적과 열 이름만 보고 설계도를 내고, 숫자는 데이터베이스가 셉니다.

AI가 낸 숫자를 믿지 못하는 사람에게 AI가 계산한 숫자를 내밀 수는 없었습니다. 그래서 역할을 나눴습니다. AI는 대시보드의 목적과 열 이름만 보고, 어떤 지표를 어떻게 셀지 적은 설계도(JSON 스펙)를 냅니다. 파일 이름이나 행, 값은 AI에게 보내지 않습니다. 숫자는 그 설계도대로 데이터베이스가 세고, 실제 열과 맞지 않는 설계도는 버립니다.
모델 선택도 에이전트의 기본값에 맡기지 않았습니다. 에이전트는 처음에 가장 성능 좋은 모델을 넣었고, 한 번 부르는 데 43~65원이 들었습니다. 비용을 지적하자 같은 시트 두 개로 세 모델을 견줬고, 가장 작은 모델도 계산할 수 없는 제안을 하나도 내지 않아 2원 안팎으로 바꿨습니다. 그 뒤로 에이전트의 규칙에 ‘가장 작은 모델부터 쓰고, 부를 때마다 비용을 보고한다’를 넣었습니다.
AI에게 맡긴 일과 맡기지 않은 일: 맡긴 일 — 목적에 맞는 지표 제안, 대시보드 설계도, 말로 고치기 / 맡기지 않은 일 — 숫자 계산, 행과 값 읽기, 영수증의 계산 / 다른 AI에게 연 일 — MCP 서버와 에이전트 API로 대시보드를 만들고 영수증을 JSON으로 돌려받습니다. 공식 MCP 레지스트리에도 올렸습니다.

화면: 말로 대시보드를 고치는 Ask. AI는 무엇을 바꿀지만 정하고, 바뀐 숫자는 다시 셉니다.

### State 4. Agents — ‘어떻게’는 에이전트가, ‘할지 말지’는 제가 정했습니다

결정을 넘긴 범위와 넘기지 않은 범위를 규칙으로 적었습니다.

처음에는 에이전트가 계획을 내면 제가 확인한 뒤에 시작했습니다. 그런데 돌아보니 9월 말부터 10월 20일까지 에이전트가 선택지를 내민 77번 중 57번은 추천안을 그대로 골랐습니다. 방향이 실제로 바뀐 곳은 대부분 질문에 답할 때가 아니라, 결과물을 보고 제가 먼저 꺼낸 말에서였습니다. 질문은 방향을 거의 바꾸지 못하고 왕복만 늘리고 있었습니다.
10월 18일, 에이전트가 시안 여섯 개를 그려 놓고 또 순서를 물었을 때 일하는 방식을 바꿨습니다.
“내가 결정하게 놔둔다면 넌 그냥 단순한 작업자일 뿐이야.” — 에이전트에게 결정을 넘기며 한 말 (2026.10.18)
그날부터 제품과 디자인, 기술은 에이전트가 근거를 붙여 정하고 진행합니다. 저는 실물을 보고, 방향이 틀렸을 때 바꿉니다. 같은 밤 에이전트는 묻지 않고 실제 서비스의 내보내기 형식 100가지로 화면 규칙을 검증했습니다. 디자인 방향도 처음 두 번은 제가 골랐지만, 그 뒤의 Pulse board와 에이전트식 편집 화면은 에이전트의 추천을 그대로 받았습니다.
에이전트와 맺은 작업 규칙: 제품 · 디자인 · 기술은 에이전트가 근거와 함께 정한다 / 운영 배포는 제가 스테이징 화면을 보고 승인한 뒤에만 한다 / 돈, 삭제, 비밀값, 실제 발송은 반드시 제 확인을 받는다 / 가장 작은 모델부터 쓰고, 부를 때마다 비용을 보고한다 / ‘됐다’에는 무엇으로, 어디까지 쟀는지를 붙인다 / 사람만 할 수 있는 마지막 단계는 대기 목록에 남긴다
여러 에이전트를 동시에 돌렸습니다. 작업 하나에 브랜치와 워크트리를 하나씩 두어 브랜치 40개, 워크트리 19개를 썼고, 워크트리마다 개발 서버 포트를 따로 주었습니다. 브랜치마다 기준 커밋과 테스트 수, 병합 상태를 적은 인수인계 메모를 남기게 했습니다. 세션끼리 부딪힐 때마다 규칙이 하나씩 늘었습니다. 테스트 데이터베이스는 세션마다 따로 쓰고, 두 세션의 운영 배포가 5초 차이로 겹친 뒤로는 배포 전에 진행 중인 다른 배포부터 확인합니다.
맡긴 결정을 다시 거둔 적도 있습니다. 에이전트는 ‘검증 먼저’라는 처음 틀에 맞춰 공개 가입과 결제, 엑셀 편집기와 AI 기능, 차트와 연동 등 네 갈래를 ‘하지 않을 것’으로 골랐습니다. 하지만 목표의 틀은 이미 ‘판정 전에도 서비스다운 서비스’로 바뀐 뒤였습니다. 네 갈래를 모두 만들기로 뒤집고, 결제만 미뤄 첫 30일을 무료로 열었습니다. 그 뒤로 에이전트가 무언가를 하지 않겠다고 제안할 때는 어떤 목표를 기준으로 했는지 한 줄을 붙이게 했습니다.

### State 5. Gates — 꼭 지켜야 하는 일은 지시문 대신 게이트로

글로 적은 규칙이 지켜지지 않을 때는, 어기면 멈추는 장치로 바꿨습니다.

“예외 없이 일어나야 하는 일은 게이트로, 알아 두면 되는 일은 지시문으로 보낸다.” — 제가 정한 에이전트 운영 원칙
에이전트에게 ‘한국어로 보고하라’고 글로 적어 두었지만 다섯 번 어겼습니다. 그래서 글로 된 규칙 대신, 한국어가 아닌 보고를 내보내려 하면 그 자리에서 막는 훅을 달았습니다. 10월 26일부터 11월 6일까지 123번을 막았습니다.
화면 넘침도 같은 방식으로 풀었습니다. 업로드 알림이 카드 밖으로 넘친 화면을 제가 짚은 뒤, 일곱 가지 화면 폭에서 넘침과 말줄임, 빈 칸을 재고 하나라도 걸리면 실패로 끝나는 검사를 만들었습니다. 화면을 바꿨다고 보고하기 전에는 이 검사를 반드시 통과해야 합니다. 넘침은 26곳에서 0곳으로, 말줄임은 22곳에서 0곳으로 줄었습니다.
에이전트가 스스로 돌리는 검증: 자동 테스트 284개 → 703개. 날짜 버그를 겪은 뒤로는 시계를 400일 뒤로 돌려 한 번 더 돌립니다. / 내보낸 Excel 파일을 다시 계산해 데이터베이스 값과 맞는지 확인합니다. / MCP 서버 검사 도구의 경고 9개 → 0개 / 10월 31일 보안 점검에서 찾은 높음 1건, 중간 4건은 같은 날 고쳐 배포했습니다. / 10월 25일에 건 장치 네 가지 — 한국어 검사, 주간 보안 점검, 운영 되돌림 확인, 화면 빈칸 검사. 운영보다 오래된 커밋을 올리는 경우 11가지를 일부러 만들어, 되돌림 확인이 멈추는지 시험했습니다.

### State 6. Now — 만드는 양은 에이전트가 늘려도, 수요는 늘려 주지 않습니다

## 02 IoT 게이트웨이 관리 SaaS — 웹 어드민 리뉴얼

- URL: https://www.309designlab.com/work/iot-saas
- 기간: 2026.06 — 2026.10
- 역할: PM · UX/IA · 디자인 시스템 도입 · 프론트엔드 리드
- 플랫폼: 웹 어드민 (375px부터 반응형 · 다크 모드)
- 범위: 진단, IA 정리, 권한 체계, 디자인 시스템 도입, 검증 하네스, UAT
- 결과: 0→974개 화면 코드에 들인 디자인 토큰 / 15→0곳 화면 코드에 흩어져 있던 역할 분기 / 0건 두 차례 UAT의 결함 (72 · 77개 항목) (리뉴얼 브랜치와 테스트 서버 기준입니다. 병합과 운영 배포는 고객사 팀이 결정합니다.)
- 산출물: 진단 보고서, 목표 IA · 사이드바, 권한 표 · 등급 관리 화면, 디자인 시스템 도입 · 호환 레이어, 목업 백엔드 · 캡처 하네스, UAT 2회 · 병합 요청 PR

**이름도 경로도 제각각이던 관리 화면을, 하나의 메뉴와 권한, 디자인 시스템으로 모았습니다**

센서와 컨트롤러를 묶는 게이트웨이를 원격으로 관리하는 B2B SaaS입니다. 같은 기능인데도 화면과 이름, 경로가 제각각이었고, 역할마다 다른 화면이 코드 곳곳에서 갈라져 있었습니다. 주말에만 일하는 1인 체제로 진단부터 UAT까지 이끌었고, 구현은 AI 에이전트와 함께했습니다. 고객사와 제품의 이름, 실제 화면은 공개하지 않고 구조와 숫자로만 설명합니다.

### Brief — 같은 기능인데도 화면과 이름, 경로가 제각각이었습니다

관리 화면에는 같은 일을 하는 화면이 여러 개 있었고, 메뉴에는 없는데 주소로만 열리는 화면도 있었습니다. 역할에 따라 보여 줄 것을 화면 코드 안에서 직접 갈랐고, 디자인 토큰 없이 스타일을 파일마다 따로 적었습니다.
중간 진단의 결론은 디자인 토큰이 없는 것이 가장 큰 병목이라는 것이었습니다. 그래서 세 가지를 목표로 잡았습니다.

1. 현행 IA를 갈아엎지 않고 정리하고 수렴하기
2. 역할 차이를 화면 코드가 아니라 권한으로 표현하기
3. 새로 세우지 않고 기존 디자인 시스템을 도입하기

### State 1. Diagnosis — 고치기 전에 먼저 셌습니다

화면마다 몇 줄인지, 어디서 갈라지는지부터 숫자로 셌습니다.

고치기 전에 지금의 상태를 셌습니다. 어떤 화면이 몇 줄인지, 같은 기능이 몇 군데에 따로 있는지, 역할에 따라 화면이 몇 번 갈라지는지, UI 라이브러리를 몇 군데서 직접 쓰는지를 보았습니다. 숫자로 세어 두어야 나중에 같은 방법으로 다시 재서 얼마나 줄었는지 말할 수 있습니다.
진단에서 센 것: 게이트웨이 화면 10개 파일 3,464줄 · 설정 2,426줄 · 대시보드 1,513줄 / 실제 데이터와 연결되지 않은 프로토타입 화면 7개 (6,607줄) / 메뉴 없이 주소로만 열리는 화면 / 디자인 토큰 0개, 스타일을 직접 적은 파일 29개 / Ant Design을 직접 쓰는 곳 48개 파일, 약 600곳 / 화면 코드 안의 역할 분기 15곳

### State 2. IA — 메뉴를 새로 짜지 않고, 있는 것을 모았습니다

모든 역할이 같은 사이드바를 보고, 도메인마다 주소를 하나로 정리했습니다.

운영 중인 서비스라 메뉴를 처음부터 다시 짜는 대신, 원칙을 ‘갈아엎지 않고 정리·수렴한다’로 정했습니다. 같은 일을 하는 화면은 하나로 합치고, 도메인마다 주소를 하나만 두었습니다. 따로 있던 관리자 화면은 사용자 관리 안으로 들어갔고, 흩어져 있던 설정은 구역 단위의 장비 설정 두 탭으로 다시 묶었습니다.
정리한 사이드바 — 모든 역할이 같은 메뉴를 봅니다: 대시보드 / 모니터링(그래프·알람) / 운영(업체·사이트·게이트웨이·제어 그룹·인증 키) / 관리(사용자·권한 관리·환경 설정)
역할마다 메뉴를 따로 그리지 않습니다. 무엇이 보이고 무엇을 할 수 있는지는 권한이 정합니다.

### State 3. Access — 역할의 차이를 화면이 아니라 권한으로 옮겼습니다

역할 4개 × 리소스 20개 × 동작 6개로 권한 표를 만들고, 허용하지 않은 것은 모두 막았습니다.

역할마다 화면을 따로 만들면, 화면이 늘 때마다 분기도 함께 늘어납니다. 원칙을 ‘역할 차이는 권한으로 표현한다’로 정하고, 화면 코드가 역할 이름 대신 권한을 묻도록 바꿨습니다. 기본은 모두 막아 두고(default deny) 권한 표에서 허용한 것만 엽니다. 권한 등급을 관리하는 화면도 새로 만들었고, 승인을 기다리는 계정은 이제 404 대신 ‘승인 대기’ 화면을 봅니다.
권한 표: 역할 4개 — 플랫폼 운영자 · 회사 관리자 · 일반 사용자 · 미승인 / 리소스 20개 × 동작 6개 / 화면 코드 안의 역할 분기 15곳 → 0곳 / 역할별 접근 점검 48/48 통과 / 남은 한계 — 직접 만든 등급은 아직 브라우저에만 저장됩니다

### State 4. System — 디자인 시스템을 새로 만들지 않고, 들여왔습니다

기존 디자인 시스템(309 DSG)의 토큰과 컴포넌트를 들이고, 호환 레이어로 한 번에 바꿨습니다.

목표는 새 시스템을 세우는 것이 아니라, 이미 있는 자산을 들이는 것이었습니다. 309 DSG의 토큰 974개(기본 326개, 의미 435개 포함)를 Ant Design 테마와 CSS 변수 양쪽에 넣고 컴포넌트 23개를 들였습니다. 모달과 스피너, 툴팁은 감싸는 컴포넌트를 새로 만들었습니다. 2개 파일, 605줄의 호환 레이어가 37개 파일의 133곳을 한 번에 바꿨습니다.
하다 보니 바꿔야 할 단위가 보였습니다. 화면이 아니라 공용 컴포넌트였습니다. 공용 컴포넌트를 바꾸자 30개가 넘는 화면이 화면 코드를 한 줄도 건드리지 않고 새 시스템으로 넘어갔습니다. 회사마다 brand.json 하나로 브랜드 색을 바꿔 쓸 수 있게 해 화이트라벨도 열어 두었습니다.
결정 — 예외는 고치고, 다시 생기지 않게 검사로 막는다: 손으로 만든 예외 때문에 같은 UI가 화면마다 다르게 보이는 곳이 있었습니다. 하나씩 고친 뒤 구조 규칙 6개를 포함한 검사 3개(lint:design)를 만들어, 예외가 다시 들어오면 검사가 실패하게 했습니다.
이유: 고쳐 둔 예외가 다시 들어오면 같은 UI가 화면마다 달라지는 일이 되풀이되기 때문입니다.
도입 결과 (7월 말 ~ 8월 초): DSG를 쓰는 화면 파일 0.6% → 26.1%, 그 사이 앱 코드는 3.4%만 늘었습니다 / 대시보드 1,513줄 → 1,032줄 · 게이트웨이 목록 1,489줄 → 910줄 / 게이트웨이 편집 690줄 → 118줄 · 사이트 목록 1,027줄 → 160줄 / 핵심 화면 32개 파일에서 Ant Design 직접 사용 0 / 첫 화면 로딩 4,330KB → 2,909KB (−33%) · 차트 라이브러리 2개 → 1개 / 대비가 부족한 색 조합 8개 → 글자 전용 토큰 5개, 16개 조합 모두 AA 통과

### State 5. Verify — 에이전트가 구현하고, 하네스가 확인했습니다

주말 1인 체제에서 커밋 117개 중 106개를 AI 에이전트가 썼습니다.

주말에만 일하는 1인 체제였기 때문에 일을 나눴습니다. IA와 권한 체계 같은 결정까지 근거를 붙여 에이전트에게 맡기고, 대신 결과를 사람이 일일이 열어 보지 않아도 확인할 수 있는 장치를 함께 만들었습니다. 고객사 저장소로 옮긴 뒤의 리뉴얼 브랜치에서, 병합을 뺀 커밋 117개 중 106개를 에이전트가 썼습니다.
목업 백엔드: 백엔드 스키마에 맞춘 목업을 개발 빌드에서만 켜지게 만들었습니다. 운영 빌드로 새어 나간 곳은 없습니다.
캡처 하네스: 역할 4개 × 모든 화면 × 화면 폭 3개를 한 번에 찍습니다. 9월 5일까지 1,081장을 찍었고 실패는 0건이었습니다.
UAT 1·2차: 10월 2일과 9일에 72개, 77개 항목을 점검해 결함 0건으로 넘겼습니다. 장비 제어 명령은 0.5~4.8초 안에 화면에 반영됐고, 시험 뒤 모두 원래대로 되돌렸습니다.

## 03 O-YOGA 웹사이트 리뉴얼

- 기간: 2026.10 — 2026.11
- 역할: PM · 크리에이티브 디렉션 · UX · AI 협업 구현
- 플랫폼: 웹 (모바일 · 데스크톱)

- 산출물: 사이트 진단, 검색 기본기 — 메타 · 구조화 데이터 · 사이트맵 · llms.txt, 방향 시안 4개와 다섯 번째 안, 6개 페이지 · 월별 시간표 데이터, 로고 드로잉 · 안개 모션, 런칭 · 옛 주소 연결

**블로그와 카카오톡으로 흩어지던 요가원을, 다시 한 사이트로 모았습니다**

2017년부터 서울과 제주에서 요가 수업과 지도자 과정을 운영해 온 O-YOGA의 웹사이트입니다. 예전 사이트의 버튼 60개는 모두 블로그와 카카오톡, 네이버 예약으로 나가고 있었습니다. PM이자 크리에이티브 디렉터로 진단과 방향, 콘텐츠 구조를 정했고, 구현은 AI 에이전트와 함께했습니다. 11월 3일, 고객 승인과 함께 런칭했습니다.

### Brief — 디자인보다 먼저, 자산을 사이트로 되돌려야 했습니다

10월 28일에 진단한 예전 사이트는 Webflow로 만든 8개 페이지였습니다. 방문을 재는 도구가 하나도 없었고, 사이트맵과 robots, 구조화 데이터, h1도 없었습니다. 이미지 216장 중 의미 있는 대체 텍스트가 붙은 것은 8장이었습니다. 무엇보다 버튼 60개가 모두 사이트 밖으로 나갔습니다. 블로그로 30개, 카카오톡으로 23개, 네이버 예약으로 7개였습니다.
그 사이 블로그에는 시간표 글 108개, 지도자 과정 글 41개, 이야기 글 495개가 쌓여 있었습니다. 진단의 결론은 디자인보다 먼저, 이 자산들을 사이트로 되돌리는 것이었습니다.

1. 찾히고 가볍고 붙잡는 사이트로, 기본기부터 고치기
2. 블로그에 흩어진 시간표와 이야기를 사이트 안으로 되돌리기
3. ‘고요’를 사진이 아니라 움직임으로 보여 주기

### State 1. Audit — 버튼 60개가 모두 사이트 밖으로 나가고 있었습니다

시안을 그리기 전에, 찾히고 가볍고 붙잡는 사이트로 기본기부터 고쳤습니다.

시안을 그리기 전에 하루 동안 예전 사이트 위에서 기본기부터 고쳤습니다. 커밋 11개로 끝난 1단계입니다.
찾히게: 언어와 메타 정보, h1을 바로잡고 구조화 데이터와 사이트맵, robots, llms.txt를 더했습니다. AI 검색 크롤러도 막지 않았습니다.
가볍게: Webflow CDN의 이미지를 AVIF로 옮겨 50.3MB를 3.44MB로, 나머지 이미지는 6.34MB를 0.57MB로 줄였습니다.
붙잡게: 스크롤해도 따라오는 메뉴와 모바일 예약 버튼, 자주 묻는 질문을 더해 사이트 안에서 답을 찾게 했습니다.

화면: 리뉴얼 전 사이트. 버튼은 모두 블로그와 카카오톡, 네이버 예약으로 나갔습니다.

### State 2. Direction — 네 방향을 그리고, 둘을 섞어 다섯 번째를 만들었습니다

첫 시안 4개를 접고, 감정이 다른 방향 A–D를 실제 사진과 움직임으로 그렸습니다.

첫 시안 네 개는 구성과 컨셉, 모션, 비주얼이 모두 부족하다고 보고 접었습니다. 다시 그린 네 방향은 각자 다른 감정 하나를 맡았고, 사진도 방향마다 색을 다르게 보정했습니다.
A · 고요 — 고요를 연습하는 곳: 로딩의 작은 원이 화면 전체로 열리고, 사진 위로 안개가 흐릅니다.
B · 해방감 — 비우러 오세요: 머릿속의 소음이 스크롤이나 4초 숨쉬기로 흩어지고, 원이 열리며 스튜디오가 보입니다.
C · 지금 — 하루의 빛: 지금 서울의 하늘과 해, 달. 다음 수업을 알려 주는 한 문장과 하루의 시간 막대.
D · 몰입 — 섬과 도시: 서울에서 제주까지 네 장면이 서로 녹아들고, 커서를 따라 물결이 입니다.
결정 — E · 고요의 원점 — A와 D를 섞고, 블로그를 안으로: A의 열리는 원과 안개, 종이 위의 편집 레이아웃을 바탕에 두고, D의 장면(서울 → 함께 → 제주 → 리트릿)을 홈 한가운데의 작은 원 안에서 열리게 했습니다. C에서는 첫 화면의 ‘다음 수업’ 한 줄만 가져왔습니다.
이유: 블로그와 카카오톡으로 나가던 길을 사이트로 되돌리는 것이 진단의 결론이었습니다. 그래서 블로그 글을 사이트의 콘텐츠로 다시 쓰는 일까지 이 방향에 넣었습니다.
첫 시안을 접으며 배운 것: 색 보정 없이 찍은 사진을 그대로 쓰면 값싸 보입니다 / 큰 한글 제목은 가는 고딕보다 명조(마루부리)가 힘이 있습니다 / ‘O’를 모양으로 반복하는 것은 얕습니다. 열리는 원, 비우는 공간처럼 이야기의 장치로 써야 합니다 / 제품 UI용 금지 목록을 브랜드 사이트에 그대로 적용하면 편집 디자인의 언어를 잃습니다

화면: 방향 B — 머릿속을 채운 말들이 흩어지는 첫 화면, 방향 C — 지금 시각의 하늘과 다음 수업 한 문장

### State 3. Structure — 시간표를 찾으러 블로그까지 가지 않아도 되게

블로그 글을 옮기지 않고 다시 써서, 6개 페이지 안에 시간표와 선생님, 과정을 담았습니다.

블로그 글을 그대로 옮기면 네이버의 중복 문서 판정에 걸립니다. 그래서 옮기지 않고 사이트에 맞게 다시 쓴 뒤 원문으로 가는 링크를 붙였습니다.
사이트는 홈, 시간표, 선생님, 지도자 과정, 저널과 이야기 글의 6개 페이지입니다. 홈 첫 화면은 서울 시각을 기준으로 다음 수업을 알려 주고, 선생님 페이지에는 이번 달에 맡은 수업이 시간표에서 자동으로 채워집니다. 메뉴는 시간표, 선생님, 지도자 과정, 이야기 네 개와 ‘체험 수업 예약’ 버튼 하나입니다.

화면: 11월 시간표 — 오늘 남은 수업, 평일 시간표 — 오늘 칸과 다음 수업, 홈 — 다음 수업 한 줄, 시간표 — 오늘 남은 수업, 지도자 과정 — 200시간의 구성

### State 4. Motion — 고요를 움직임으로 — 로고 한 줄과 안개

원래 로고를 지키고, 한 줄로 그려지는 움직임과 사진 위의 안개로 분위기를 만들었습니다.

로고는 바꾸지 않았습니다. 대신 원래의 한 줄 로고가 실제로 한 줄로 그려지게 해, 첫 화면과 페이지 전환, 바닥글에서 같은 움직임을 반복합니다. 첫 화면 사진 위에는 WebGL로 안개를 흘렸고, 서울에서 제주로 이어지는 장면에서는 브라우저가 만든 파도 소리를 원하는 사람만 켤 수 있습니다. 움직임 줄이기를 켠 사람에게는 움직임을 덜어 냅니다.

화면: 로고가 한 줄로 그려지는 네 단계, 홈 첫 화면 — 안개와 다음 수업, 서울에서 제주로 이어지는 장면 — 제주

### State 5. Launch — 11월 3일, 고객 승인과 함께 런칭했습니다

미리보기 주소에서 확인을 받고, 옛 주소 13개를 새 페이지로 이어 붙였습니다.

11월 1일부터 미리보기 주소에서 고객의 확인을 받았고, 11월 3일 저녁 승인과 함께 런칭했습니다. 화면 9개를 375, 768, 1440 세 가지 폭에서 확인해 오류가 없었고, 옛 주소 13개는 새 페이지로 301 연결했습니다. 예를 들어 소개 페이지는 선생님으로, 프로그램 페이지는 지도자 과정으로 이어집니다.
아직 남은 일: 애널리틱스 ID가 비어 있어 방문을 아직 재지 못합니다 / 자바스크립트가 꺼진 환경에서는 시간표 글의 약 30%만 보입니다 / 예약은 여전히 네이버 예약과 카카오톡으로 이어집니다 / 시간표는 매달 데이터 파일을 직접 고쳐 올립니다

화면: 지도자 과정 — 200시간 구성, 지도자 과정 — 묻고 답하기, 저널 — 블로그에서 다시 쓴 글

## 04 페이히어 디자인 시스템 & 2.0 리뉴얼

- URL: https://www.309designlab.com/work/payhere-design-system
- 기간: 2022.11 — 2023.12
- 역할: 시니어 프로덕트 디자이너 · 디자인 시스템 구축 리드
- 플랫폼: 태블릿 POS · PC · 모바일
- 범위: 파운데이션, 컴포넌트, 토큰, 사내 교육, 2.0 리뉴얼
- 결과: 3.5→1.3일 디자이너 평균 업무 처리 기간 / 4→2.5일 프론트엔드 평균 개발 기간 / 40%+ 디자이너·개발자 간 협업 효율 향상 (하루 업무시간 기준 — 디자이너 10–12시간, 프론트엔드 10–14시간)
- 산출물: 파운데이션 — 컬러 · 타이포 · 그리드 · 그림자 · 보더, 컬러 토큰 체계, Figma 컴포넌트 라이브러리, 브랜드 가이드라인, 사내 교육 세션, 2.0 리뉴얼

**버튼 하나의 크기도 제각각이던 팀에, 같은 언어를 만들었습니다**

페이히어에 합류했을 때 팀에는 디자인 시스템을 만들어 본 사람이 없었고, 저에게는 리딩이 핵심 역량으로 주어졌습니다. 디자인 시스템을 직접 제안해 구축을 이끌고, 같은 시기에 진행된 2.0 리뉴얼까지 정해진 마감일에 런칭했습니다.

### Brief — 시스템보다 먼저, 같은 기준이 없었습니다

입사 당시 저에게 요구된 핵심 역량 중 하나는 리딩이었습니다. 디자인 챕터 리드가 따로 있어 의아했지만, 디자인 시스템을 만들면서 그 이유를 알게 되었습니다. 리드와 팀원 모두 디자인 시스템을 구축해 본 경험이 없었고, 그 중요성은 점점 커지고 있었습니다.
그래서 디자인 시스템을 먼저 만들어야 한다고 제안했고, 두 가지 미션을 맡았습니다.

1. 팀원들의 디자인 시스템 이해도 높이기
2. 디자인 시스템 구축하기

### State 1. Before — 같은 ‘저장’ 버튼도 화면마다 크기가 달랐습니다

2.0 이전 화면의 버튼 7종을 재어 보니 너비·높이·글자 크기가 모두 달랐습니다.

당시 팀에서는 버튼 하나의 사이즈조차 통일되지 않았고, 디자인 가이드는 각자의 기준에 의존하고 있었습니다. 아래는 2.0 이전 화면에서 가져온 버튼들입니다. 같은 ‘저장’인데도 너비와 높이, 글자 크기가 모두 다릅니다. 정의되지 않은 기준이 그대로 사용성의 차이로 이어지고 있었습니다.
Before — 2.0 이전 화면의 버튼 7종: 같은 ‘저장’ 버튼인데도 너비·높이·글자 크기가 모두 달랐습니다.
After — 같은 버튼을 solid · outline · text 토큰으로 정의했습니다 (P2_token_color / ButtonTokens / primary).

### State 2. Align — 혼자 만드는 시스템이 아니라, 함께 쓰는 시스템으로

열 명의 팀원과 1:1로 만나고, 워크숍으로 생각과 목표를 정렬했습니다.

시스템을 그리기 전에 먼저 팀원들을 만났습니다. 시스템 하나에도 많은 가이드라인이 필요했고, 동시에 리뉴얼도 준비해야 했기에 대화와 조율에 많은 시간을 썼습니다.
1:1 미팅: 열 명의 팀원과 한 사람씩 만나 지금의 문제와 해결책을 이야기했습니다.
워크숍: 팀원들의 생각을 정렬하고, 시스템이 달성할 목표를 명확히 세웠습니다.

### State 3. Sidekick — 배트맨에게 로빈이 있듯, 두 번째 커뮤니케이터를 세웠습니다

가장 업무 능력이 뛰어난 팀원과 싱크를 맞춰 또 한 명의 커뮤니케이터로 세웠습니다.

결정 — 조율을 나눠 맡을 사람을 먼저 세운다: 시스템 가이드라인과 리뉴얼 준비가 겹치면서 대화와 조율에 많은 시간이 들었습니다. 가장 업무 능력이 뛰어난 팀원을 설득해 저와 싱크를 맞춘 뒤, 또 하나의 커뮤니케이터로 세웠습니다.
이유: 덕분에 다시 실무에 집중할 시간을 확보했습니다. 주말과 연휴를 반납하며 진행했고, 정해진 마감일에 맞춰 런칭했습니다.

### State 4. Foundation — 컬러·타이포·그리드부터 같은 기준에서 출발하게

파운데이션을 정의하고 컬러 토큰으로 연결했습니다.

모든 화면이 같은 기준에서 출발하도록 파운데이션부터 정리했습니다. 컬러 스타일과 시맨틱 컬러, 타이포그래피, 레이아웃 그리드, 그림자와 보더를 정의하고 이를 컬러 토큰으로 연결했습니다.

화면: 컬러 스타일, 시맨틱 컬러, 타이포그래피, 레이아웃 그리드, 그림자, 보더

### State 5. Components — 매장에서 가장 자주 쓰는 컴포넌트부터

결제와 상품 선택처럼 반복되는 동작의 컴포넌트부터 정의했습니다.

결제와 상품 선택처럼 POS에서 반복되는 동작을 이루는 컴포넌트부터 정의했습니다. 버튼과 입력 필드, 탭, 키패드, 상품 카드, 리스트가 그 시작이었고, 각 컴포넌트는 앞에서 정한 토큰만으로 그려지도록 했습니다.
Figma 기반 컴포넌트 라이브러리를 구축하고 브랜드 가이드라인을 체계화했으며, 사내 교육 세션을 운영했습니다. 디자인을 문서로 정리해 사내 디자이너와 개발자 모두가 디자인 시스템을 활용할 수 있도록 했습니다.

화면: Primary 버튼, 컬러 토큰, 입력 필드, 탭, 키패드, 상품 카드, 리스트 아이템, 모달 리스트, 사이드바 리스트

### State 6. 2.0 Renewal — 시스템 위에서 2.0 리뉴얼을 함께 진행했습니다

일관성과 성장, 두 가지 약속으로 리뉴얼을 이끌었습니다.

리뉴얼은 단순한 디자인 변경이 아니라 새 디자인 시스템 구축과 동시에 진행되어야 했습니다. 하루에도 여러 건의 예외가 생겼고, 작업하는 화면이 늘어날수록 일관성을 지키는 일은 더 어려워졌습니다. 킥오프 전 워크숍에서 팀과 두 가지를 약속했습니다. 일관성을 지킨다. 그리고 이번 리뉴얼을 UI 디자이너에서 프로덕트 디자이너로 성장하는 시작점으로 삼는다.
자리로 찾아가기: 하루 중 제 자리보다 팀원들 자리에서 대화하는 시간이 더 많았습니다. 짧은 시간에 디테일과 피드백을 주고받기에 가장 효율적이었습니다.
데일리 스크럼: 디자인 스타일 이슈를 모으고 업데이트하는 시간으로 썼습니다.
주간 회의: 프로젝트 전체의 일관성을 지키기 위한 집중 논의 자리로 삼았습니다.
결정 — 2.0은 시안의 다양성을 줄인다: 1.0이 시안의 가시성에 집중했다면, 2.0은 시안의 다양성을 줄여 기획 의도를 더 분명하게 드러내는 방향으로 발전했습니다.
이유: POS는 기능이 많고, 사장님들은 바쁜 순간에 화면을 봅니다. 결제와 직결되는 입력 위치를 분명히 하고 복잡한 작업을 단순하게 표현했습니다. 디자인 시스템은 이 단순함을 구현하는 도구였습니다.

화면: 간편 로그인 — 전화번호 입력 (공동 작업), 매장 분석 — 매출 달력 (공동 작업)

### State 7. Outcome — 속도가 빨라졌고, 리뷰의 질문이 바뀌었습니다

처리 기간이 줄었고, 팀 모두가 사용자 관점으로 묻기 시작했습니다.

디자이너의 평균 업무 처리 기간은 3.5일에서 1.3일로, 프론트엔드의 평균 개발 기간은 4일에서 2.5일로 줄었습니다. 더 큰 변화는 리뷰에서 일어났습니다. 리뉴얼 전에는 디자인 챕터 리뷰에서 피드백이 거의 없었습니다. 각자의 컴포넌트와 스타일을 다른 디자이너와 맞출 필요가 없었기 때문입니다. 이제는 모두가 이렇게 묻습니다.
리뉴얼 이후 디자인 챕터 리뷰에서: “사용자들이 이 기능을 어떻게 사용할까요?” “우리 팀에서는 이렇게 개선했는데, 동일한 기능이라면 협의가 필요할 것 같습니다.”
팀원 모두가 프로덕트 디자이너로서 사용자 중심으로 생각하고 협업하게 되었습니다. 디자인 시스템은 이후 플랫폼 디자이너를 채용할 만큼 중요한 요소로 자리 잡았고, 1년이 지나 한 개발자에게서 이런 말을 들었습니다.
“당신이 그때 디자인 가이드를 만들지 않았다면, 지금 우리 프로덕트들은 다 무너졌을 겁니다.” — 페이히어 개발자
기본을 단단히 쌓는 일이 어떤 차이를 만드는지, 그리고 시스템 구축을 리드하며 팀을 이끌었던 과정이 결실을 맺었다는 것을 확인한 순간이었습니다.

## 05 페이히어 도소매 2.0 — 재고 · TRS · 주문 관리

- URL: https://www.309designlab.com/work/payhere-retail
- 기간: 2023 (TRS 2023.07 — 2023.11)
- 역할: 시니어 프로덕트 디자이너 · 도소매 디자인 담당
- 플랫폼: 태블릿 POS · PC 대시보드 · 모바일
- 범위: 상품·재고 관리, 입고·거래처, 바코드, TRS 즉시 환급, 주문·픽업 알림
- 산출물: 판매자 유형 · 상품 등록, 입고 · 재고 이력 · 거래처, 모바일 재고 알림 · 바코드 스캔, PC 바코드 인쇄 · 재고 · 판매 데이터, TRS 즉시 환급 · 주문 관리, 픽업 알림톡

**옵션·묶음 상품부터 외국인 즉시 환급까지, 도소매 매장의 운영 흐름을 다시 설계했습니다**

페이히어 2.0에서 도소매(리테일) 디자인을 맡았습니다. 식료품점, 의류·잡화, 꽃집처럼 상품 구성이 복잡한 매장을 위해 상품·재고 관리를 다시 짜고, 외국인 관광객의 TRS 즉시 환급과 온라인 주문·매장 픽업을 재고와 연결했습니다.

### Brief — 도소매 매장은 상품 구조부터 다릅니다

식료품점, 의류·잡화, 꽃집 같은 도소매 매장은 옵션과 묶음 상품, 입고와 재고 이력을 매일 다룹니다. 외국인 관광객 비중이 높은 매장에서는 여기에 즉시 세금 환급(TRS)과 온라인 주문·매장 픽업까지 필요했습니다.
상품을 등록하는 순간부터 고객이 주문한 상품을 받아 가는 순간까지, 매장의 흐름 전체를 하나로 잇는 일이었습니다.

### State 1. Context — 판매자 유형부터 상품 구조까지

도소매 유형을 따로 두고, 옵션과 묶음 상품을 편하게 관리하게 했습니다.

페이히어 2.0에서는 매장이 판매자 유형을 고르도록 바뀌었습니다. 도소매(POS)는 식료품점, 의류·잡화, 선물·공예, 반려동물, 꽃집, 인테리어 매장을 위한 유형입니다. 옵션과 묶음처럼 다양한 형태의 상품을 편리하게 관리하고, 도소매에 특화된 재고 관리를 쓸 수 있어야 했습니다.
사용자 리서치로 페인포인트를 도출해 UX 전략을 세우고, 재고와 정산 기능을 직관적으로 다시 설계했습니다. 바코드 스캔과 AI 예측 주문 기능을 도입해 매장 운영 자동화에 기여했습니다.

화면: 판매자 유형 선택 — 도소매 2.0, 묶음 상품 추가

### State 2. Inventory — 입고부터 재고 이력, 거래처까지

상품을 받는 순간부터 재고 이력과 거래처까지 태블릿 POS 안에서 처리합니다.

상품을 받는 순간의 입고 접수부터 재고가 바뀐 이력, 거래처 관리까지 태블릿 POS 안에서 처리할 수 있도록 설계했습니다.

화면: 입고 — 접수 내역, 재고 히스토리, 거래처 관리, 주문 관리 — 검색 완료

### State 3. Anywhere — 매장 밖에서도, PC에서도 같은 재고를 봅니다

모바일은 재고 부족과 바코드 입고를, PC는 바코드 인쇄와 데이터를 맡았습니다.

사장님이 매장에 없을 때도 재고 부족을 알 수 있도록 모바일 홈에 재고 부족 배너를 두었습니다. 입고할 상품은 바코드 스캔으로 바로 찾게 하고, 스캔 툴팁과 카메라 접근 권한 안내도 함께 설계했습니다.
PC 대시보드에서는 도소매 전용 바코드 인쇄와 재고 관리, 입·출고·조정 요약과 활동 내역, 판매 상세 내역을 다뤘습니다. 매출·재고·고객 행동 데이터를 사업자가 읽을 수 있는 인사이트로 보여 주고, 물류 흐름을 한눈에 보게 하는 것이 목표였습니다.

화면: 홈, 홈 — 재고 부족 배너, 입고 — 상품 선택에서 바코드 스캔 완료까지, 바코드 스캔 안내, 입고 › 검색 › 바코드 스캔, 바코드 인쇄 — 상품 적용, 재고 관리 — 내역 있음, 활동 내역 조회, 판매 상세 내역

### State 4. Hypotheses — 외국인 관광객이 많은 매장의 요청에서 시작했습니다

TRS와 픽업 요청을 세 가지 가설로 나눴습니다.

외국인 관광객 비중이 높은 한 렌즈 브랜드는 매장에서 바로 세금을 환급받는 TRS(Tax Refund Service)를 원하는 고객이 많았습니다. 동시에 온라인으로 주문하고 매장에서 픽업하는 경험을 개선하고, 주문 상태와 재고를 실시간으로 맞추고 싶어 했습니다. 매장에서의 불필요한 대기를 줄이고 고객이 상품을 원활하게 받게 하는 것이 핵심 문제였습니다. 문제를 세 가지 가설로 나눴습니다.
가설 1 — 함께 있으면 더 산다: TRS와 온라인 주문·픽업을 함께 제공하면 해외 여행객의 편의가 커지고 구매 전환이 늘어난다.
가설 2 — 알림이 방문을 바꾼다: 주문과 재고를 연동하고 픽업 준비를 실시간으로 알리면, 고객이 주문 상태를 미리 알고 효율적으로 방문한다.
가설 3 — 기다림이 줄어든다: 픽업 알림과 실시간 재고 연동으로 대기 시간과 재고 불확실성에서 오는 불만을 줄이고 매장 운영도 효율적이 된다.

### State 5. Test Build — 테스트 빌드로 먼저 확인하고, 피드백으로 고쳤습니다

테스트 빌드 → 2차 미팅 피드백 → 주문 상태와 알림 개선 순서로 진행했습니다.

테스트 빌드: TRS 기능과 주문 관리를 연동한 테스트 빌드를 먼저 만들어, 온라인 주문 후 매장에서 간편하게 픽업하는 초기 기능을 구현했습니다.
2차 미팅: 초기 버전을 도입한 뒤 피드백을 모았습니다. 고객이 미리 주문한 품목을 매장에서 쉽게 바꾸고 싶어 한다는 요구가 나왔습니다.
개선: 재고 상태에 따라 주문 상태를 ‘상품 준비중’과 ‘출고 처리중’으로 나눠 보여 주고, 상태가 바뀔 때마다 고객에게 실시간으로 알리도록 했습니다.
결정 — 변경 요청은 새 화면 대신 기존 상품 탭으로: 사전 주문한 품목을 매장에서 쉽게 바꾸고 싶다는 요구가 나왔을 때, 새 기능을 만드는 대신 기존 상품 탭을 활용해 간편하게 대응했습니다.
알림톡 · 픽업 준비 완료: [수령 안내] 준비가 완료되었습니다. 매장을 방문해주세요. (주문 상태가 바뀔 때마다 고객에게 자동으로 보냅니다.)

화면: 결제 — 즉시 환급 정보 입력, 오류에서 완료까지, 결제 › Tax Refund 신청, 즉시 환급 — 정보 입력, 주문 상세

### State 6. Outcome — 고객은 매장에 오기 전에 주문 상태를 압니다

재고와 연동된 주문 관리·알림으로 고객 불편을 줄이고 매장 운영을 효율화했습니다.

고객이 매장을 방문하기 전에 주문 상태를 쉽게 확인할 수 있도록, 재고 상태와 연동된 주문 관리와 알림 시스템을 만들었습니다. TRS를 온라인 주문·매장 픽업과 연동해 해외 여행객의 구매 동기를 강화했고, 고객층의 특성을 고려한 맞춤 솔루션으로 고객 만족과 매출에 긍정적인 영향을 주었습니다.
이 작업은 페이히어 온라인 스토어 연동을 강화하는 계기가 되었고, 온라인 스토어에서는 이렇게 소개되었습니다.
페이히어 온라인 스토어 안내 문구: 고객이 원하는 픽업 주문, 10초 안에 도입 가능 / 링크를 통해 간편하게 픽업 예약 접수 / 온/오프라인 주문 페이히어 셀러 하나로 통합 관리 / 주문 상태가 변경될 때마다 고객에게 알림톡 무료 전송

## 06 하나은행 마이데이터 ‘하나 합’

- URL: https://www.309designlab.com/work/hana-hap
- 기간: 2021.08 — 2022.08
- 역할: 차장 · 디자인 리드
- 플랫폼: 모바일 앱
- 범위: 정보 구조, 진단, 합계부, 환테크, 합트렌드, 컴포넌트 가이드
- 산출물: 다섯 탭 정보 구조, 진단 대시보드 — 스타일 · 자금흐름 · 환테크 · 리포트, 합계부 · 지출 카테고리 아이콘, 소비엿보기 · 합트렌드 · 금융일기, 기관 연결 온보딩, 컴포넌트 가이드 · 일러스트

**흩어진 자산과 소비를 ‘합’쳐, 내 돈의 흐름이 보이게 했습니다**

하나은행 마이데이터 서비스 ‘하나 합’의 UX 설계를 총괄했습니다. 소비 패턴 시각화와 금융 건강도 진단, 자동 자산관리 기능과 맞춤형 금융 추천까지, 데이터를 보여 주는 데서 그치지 않고 나에게 의미 있는 이야기로 읽히게 만드는 것이 목표였습니다.

### Brief — 모아 보여 주는 것만으로는 흐름이 보이지 않습니다

마이데이터는 흩어진 계좌와 카드, 자산을 한곳에 모아 줍니다. 하지만 숫자가 한 화면에 모인다고 내 돈이 어떻게 흐르는지 알 수 있는 것은 아닙니다.
그래서 정보 구조를 역할별로 나눴습니다. 모으는 탭, 읽어 주는 진단, 기록하는 합계부, 또래와 비교하는 트렌드까지 — 데이터가 생활의 언어로 읽히게 하는 것이 이 서비스의 과제였습니다.

### State 1. Structure — 다섯 개의 탭으로 돈의 흐름을 나눴습니다

하나 · 자산 · 진단 · 플랜 · 인포, 다섯 탭으로 구조를 나눴습니다.

‘하나 합’은 하나 · 자산 · 진단 · 플랜 · 인포 다섯 탭으로 구성했습니다. 기관을 연결하면 흩어진 계좌와 카드, 자산이 한곳에 모이고, 진단 탭은 그 데이터를 생활의 언어로 다시 읽어 줍니다. 아래 프레임 안에서 각 탭의 전체 화면을 스크롤해 볼 수 있습니다.

화면: 하나 탭, 자산 탭, 진단 탭

### State 2. Diagnosis — 숫자를 ‘나의 이야기’로 바꿨습니다

스타일 · 자금흐름 · 환테크 · 리포트로 데이터를 생활의 언어로 읽어 줍니다.

진단 탭에는 자산관리 스타일(예비자금 선호형 같은), 그 주의 라이프스타일(‘이번주는 택배러버 스타일’), 꼼꼼한 입출금계좌 분석, 여유자금을 감지하는 자금흐름 진단, 환테크 챌린지와 환율 보고서, 자산합 리포트, 페이머니 관리, 스마트 세금관리를 담았습니다. 소비 패턴을 시각화하고 금융 건강도를 진단하는 대시보드가 핵심이었습니다.

화면: 자산관리 스타일, 자금흐름 진단, 자산합 리포트, 환테크 챌린지 — 목표 고르기, 환테크 — 나의 챌린지, 환테크 — 환율 리포트

### State 3. Ledger — 합계부 — 시세부터 지출까지, 우리집 머니케어

카테고리별 지출과 고정비, 월별 예산으로 이어지는 가계부를 설계했습니다.

합계부는 우리집의 돈을 시세부터 지출까지 관리하는 가계부입니다. 카테고리별 지출과 고정비, 월별 예산 관리로 이어지고, 지출 카테고리마다 아이콘을 그려 한눈에 구분되게 했습니다.

화면: 합계부 메인 — 칩 네 개와 상세내역, 합계부 상세

### State 4. Peers — 또래의 소비와 자산을 엿보게 했습니다

소비엿보기와 합트렌드로 또래와 비교하고, 금융일기로 알림을 모았습니다.

소비엿보기는 ‘하나가 알려주는 7월, 30대 친구들의 소비생활’처럼 또래의 소비를 보여 주고, 합트렌드는 휴가형, 주식형 투자고수처럼 또래와 자산을 비교합니다. 금융일기에서는 금융 알림을 한곳에 모아 봅니다.

화면: 소비엿보기, 합트렌드 — 휴가형, 합트렌드 — 주식형 투자고수, 금융일기

### State 5. Onboarding — 기관 연결에서 시작하는 첫 경험

무엇을 연결하는지 먼저 알리고, 기관을 고르고 연결하는 과정을 설계했습니다.

마이데이터는 기관 연결에서 시작합니다. 서비스 가입 전에 안내 팝업으로 무엇을 연결하는지 먼저 알리고, 기관을 고르고 연결하는 과정을 설계했습니다.

화면: 서비스 가입 전 안내, 기관 연결 — 기관 선택, 기관 연결

### State 6. System — 브랜드 일관성과 개발 효율을 위한 가이드

컴포넌트 가이드와 일러스트, 아이콘을 체계화했습니다.

컴포넌트 가이드와 일러스트, 아이콘을 체계화해 화면이 늘어나도 브랜드 일관성이 유지되게 하고, 개발 효율을 높였습니다.

## 07 신시아 — AI 오디오북 스튜디오

- URL: https://www.309designlab.com/work/synthya
- 기간: 2024.06 — 2024.09
- 역할: 프로젝트 PM · 서비스 기획 · UX/UI
- 플랫폼: 웹
- 범위: 스튜디오, 음성 캐스팅, 발음 사전, 보이스 클로닝, 결제, 운영 대시보드
- 결과: 10분 ePub 업로드부터 오디오북 완성까지
- 산출물: 서비스 기획 · 린 MVP 프로세스, 스튜디오 UX 구조, 음성 캐스팅 · 보이스 라이브러리, 발음 사전 · 쉼 조절, 보이스 클로닝 신뢰 가이드, 요금제 · AI 학습 데이터 대시보드

**ePub 한 권을 10분 만에 오디오북으로. AI의 결과를 사람이 다듬을 수 있게 했습니다**

AI 음성 합성 기술로 오디오북을 만드는 플랫폼, 신시아의 기획과 UX/UI를 맡았습니다. AI가 자동으로 해 주는 일과 사람이 직접 고치는 일 사이의 균형을 설계하고, MVP를 빠르게 만들기 위한 린 프로세스를 세웠습니다.

### Brief — 자동화할수록, 사람이 고칠 자리가 필요했습니다

오디오북 제작은 복잡하고 수작업이 많은 일이었습니다. 신시아는 ePub 파일만 올리면 AI가 제작 전 과정을 자동화해 10분 만에 오디오북을 만듭니다.
하지만 오디오북의 완성도는 목소리와 발음, 문장 사이의 쉼에서 갈립니다. AI가 먼저 만들고 사람이 원하는 대로 다듬을 수 있어야 했고, 내 목소리를 맡기는 기능에는 신뢰가 먼저 필요했습니다.

### State 1. Studio — 업로드하면 10분, 제작 전 과정을 자동화했습니다

ePub을 올리면 AI가 제작 전 과정을 자동화합니다.

사용자는 ePub 형식의 책 파일을 올리기만 하면 됩니다. AI가 오디오북 제작의 전 과정을 자동화해, 복잡하고 오래 걸리던 제작을 10분 만에 끝냅니다. 출판사는 더 빠르게 콘텐츠를 만들어 배포할 수 있고, 더 많은 작가의 책이 오디오북이라는 매체로 확장될 수 있습니다.
PM으로서 MVP 제작을 위한 린(Lean) 프로세스를 만들고, 기획과 디자인을 병행해 개발 리드타임을 줄였습니다. 전 과정에서 사용자가 직관적으로 접근할 수 있도록 UX 구조를 설계했습니다.

화면: 라이브러리 — 내 책 목록, 로그인

### State 2. Casting — AI가 목소리를 고르고, 사람이 바꿉니다

AI가 캐릭터별로 목소리를 매칭하고, 사용자는 원하는 스타일로 바꿉니다.

AI가 텍스트를 분석해 캐릭터마다 가장 어울리는 목소리를 자동으로 매칭하는 음성 캐스팅 로직의 기획을 지원했습니다. 사용자는 AI가 제안한 음성을 원하는 스타일로 자유롭게 바꿀 수 있습니다.
결정 — AI가 제안하고, 사람이 고친다: AI가 텍스트를 분석해 캐릭터별 목소리를 자동으로 매칭하고, 사용자는 제안된 음성을 원하는 스타일로 바꾸거나 단어의 발음을 일괄 수정하고 문장 사이의 쉼을 조절할 수 있게 했습니다.
이유: 10분 만에 끝나는 자동화의 속도를 살리면서, 오디오북의 완성도는 사용자가 직접 다듬을 수 있게 하는 것이 목표였습니다.

화면: 스튜디오 — 캐릭터별 음성, 보이스 라이브러리

### State 3. Editing — 발음과 쉼까지 세밀하게 고칠 수 있게

발음 사전과 문장 사이 정지 시간 조절을 설계했습니다.

특정 단어의 발음을 한 번에 고치는 발음 사전, 문장 사이의 정지 시간 조절처럼 오디오북의 완성도를 좌우하는 커스터마이징 기능의 UI/UX를 설계했습니다.

화면: 발음 사전 — 음성 녹음부터 발음 가이드 생성까지, 스튜디오 — 문장 편집, 스튜디오 — 발음 사전, 발음 가이드

### State 4. Trust — 내 목소리를 맡기는 일에는 신뢰가 먼저입니다

보이스 클로닝의 보안성과 신뢰성을 위한 사용성 가이드를 세웠습니다.

보이스 클로닝은 자신의 목소리를 복제해 오디오북에 쓰는 기능이라 개인 음성 데이터를 다룹니다. 데이터의 보안성과 신뢰성을 높이기 위한 사용성 가이드와 접근 전략을 함께 세워 전체 사용자 경험의 완성도를 높였습니다.

화면: 보이스 클로닝 — 보이스 랩

### State 5. Business — 요금제부터 운영 대시보드까지

네 가지 요금제와 AI 학습 데이터 관리 대시보드를 설계했습니다.

개인 작가부터 출판사까지 규모에 맞춘 네 가지 요금제, Free($0) · Self publisher($79) · Publisher($990) · Scale(문의)의 결제 화면을 설계했습니다. 운영 쪽에서는 AI 학습 데이터를 관리하는 대시보드 UX를 설계해 운영 효율을 높였습니다.
기술과 사용자 사이의 간극을 좁히는 것이 이 프로젝트에서 제 역할이었습니다. 음성 캐스팅, 커스터마이징, 보이스 클로닝 가이드가 직관적으로 이어지고 쉽게 조작되도록 인터페이스를 기획해, 기존 제작 방식보다 비용과 시간을 크게 줄이면서도 사용자 취향에 맞춘 결과물을 만들 수 있게 했습니다.

화면: 결제 — 상품 선택

## 08 알다 — 대출비교 혁신금융서비스

- URL: https://www.309designlab.com/work/alda
- 기간: 2019.08 — 2020.10
- 역할: 프로덕트 매니저 · 디자이너
- 플랫폼: 웹 · 모바일
- 범위: 대출비교 혁신금융서비스, CJ 협업 SaaS, 자산·소비, 보험 청구, 스타일 가이드
- 결과: +10% CJ 회원 프로세스 통합 후 회원가입률 / 171,085건 서비스 누적 대출 조회 (2020년 8월 기준) / 6,403억 원 서비스 총 한도 승인 금액 (대출 조회와 한도 승인은 서비스 전체 지표입니다. 혁신금융서비스 지정 기간 2019.05.15 — 2021.05.15)
- 산출물: 혁신금융서비스 메인 · 본인인증, 금리인하요구권 · 컨시어지, 대출 · 자산 · 소비 · 보험 화면, CJ 협업 회원 프로세스 통합, 보험 청구 플로우 차트, 스타일 가이드 — 타이포 · 컬러 · 아이콘

**브랜딩 디자이너에서 PM으로. 대출비교 서비스의 회원가입률을 10% 높였습니다**

알다에서 UI/UX 디자이너로 시작해 브랜딩에도 참여했습니다. 팀 리드가 퇴사하고 회사가 팀을 리빌딩하던 시기에 프로젝트를 이끌게 되었고, 자연스럽게 프로덕트 매니저 역할까지 맡았습니다.

### Brief — 디자이너로 들어가, 프로젝트를 이끄는 자리에 섰습니다

알다는 신용점수에 영향 없이 여러 금융사의 대출을 한 번에 비교하고 신청하는 혁신금융서비스였습니다. 금융 상품은 용어와 조건이 복잡해서, 사용자가 내가 받을 수 있는 최대 한도와 최저 금리를 한눈에 아는 것이 중요했습니다.
그 사이 팀 리드가 퇴사했고, 회사는 팀 전체를 리빌딩하고 있었습니다. 디자인만이 아니라 비즈니스와 기술의 요구를 함께 풀어야 하는 자리가 생겼고, 그 일을 맡게 되었습니다.

### State 1. Role — 디자이너에서 PM으로

팀 리드의 퇴사와 팀 리빌딩 속에서 PM 역할까지 맡았습니다.

알다에서의 첫 역할은 UI/UX 디자이너였지만, 브랜딩 디자이너로서의 경험을 살려 브랜드를 만들고 사용자 경험을 개선하는 프로젝트에도 참여했습니다.
팀 리드가 퇴사하면서 제가 프로젝트를 전적으로 이끌어야 하는 상황이 찾아왔습니다. 회사는 팀 전체를 리빌딩하는 중이었고, 그 과정에서 PM 역할까지 맡게 되었습니다. 도전적인 기회이자 성장의 순간이었습니다. 대표님의 신뢰와 도움 덕분에 프로젝트 전반을 리드하며 애자일한 작업 방식과 제품 개발 프로세스를 깊이 이해할 수 있었습니다.

화면: 메인, 혁신금융서비스 — 소개 · 안내사항

### State 2. Business — CJ와 함께 대출비교 SaaS 모델에 도전했습니다

두 회사의 회원 프로세스를 통합해 회원가입률을 10% 높였습니다.

‘대출비교서비스(혁신금융서비스)’를 SaaS 모델로 확장하는 새로운 비즈니스에 도전했고, CJ와의 협업으로 프로젝트를 진행했습니다.
결정 — 두 회사의 회원 프로세스를 하나로: 협업의 가장 큰 걸림돌은 회원가입이었습니다. 회원가입과 관련된 주요 이슈를 풀어 CJ의 회원 프로세스와 알다의 신규 회원 시스템을 통합했습니다.
이유: 디자인이나 사용자 경험만이 아니라 복잡한 비즈니스 요구와 기술적 요구를 함께 해결해야 하는 문제였습니다. 기획 단계부터 개발 완료까지 개발자와 애자일하게 움직였고, 그 결과 회원가입률이 10% 늘었습니다.

화면: 혁신금융서비스 — 본인인증, 금리인하요구권 — 결과, 컨시어지 — 신용 올리기, 신용대출 — 대출 계산기

### State 3. Service — 대출에서 자산·소비·보험까지

대출 비교를 중심으로 금융 생활 전반의 화면을 설계했습니다.

대출 비교를 중심으로 자산, 자동차, 부동산, 소비, 카드 상품, 보험까지 금융 생활 전반을 다루는 화면을 설계했습니다. A/B 테스트와 사용자 리서치를 바탕으로 UI를 개선하며 전환율을 최적화했고, 웹과 모바일을 아우르는 크로스플랫폼 프로젝트를 애자일로 이끌었습니다.

화면: 자산 — 메인, 자산 — 대출 상세, 자산 — 차량 유지비, 자산 — 부동산 상세, 소비 — 카드 통계, 상품몰 — 카드, 신용 관리, 알다 AI — 보험

### State 4. Flow & Style — 보험 청구 플로우와 스타일 가이드

보험 청구 흐름을 플로우 차트로, 시각 언어를 스타일 가이드로 정리했습니다.

마이데이터 기반 보험 청구 흐름을 플로우 차트로 정리하고, 타이포 스케일과 컬러, 아이콘을 스타일 가이드로 정리했습니다.

화면: 보험 청구 플로우 차트, 타이포 스케일, 컬러, 아이콘 세트

### State 5. Learned — 디자인과 PM, 두 관점을 함께 쓰게 되었습니다

기획서와 커뮤니케이션의 중요성을 몸으로 익혔습니다.

브랜딩 디자이너로 시작했지만, 알다에서의 경험은 저를 기획을 이해하고 비즈니스 마인드를 갖춘 PM으로 성장시켜 주었습니다. 디자인 이상의 비즈니스적 사고와 기획력을 키우는 계기였고, 기획서 작성의 중요성과 커뮤니케이션의 핵심을 체득한 경험이었습니다.
이 경험을 바탕으로 이제는 디자인과 PM, 두 가지 관점을 모두 활용해 문제를 해결하고 팀을 이끌고 있습니다.

## 09 코레일 피복관리 시스템

- URL: https://www.309designlab.com/work/korail
- 기간: 2025
- 역할: 프로젝트 PM · 서비스 기획 · UI/UX
- 플랫폼: 웹 (신청자 · 관리자)
- 범위: 신청자·관리자 화면, 서비스 플로우, 시안 분석 보고서, 클라이언트 커뮤니케이션
- 산출물: 현장 인터뷰 · 기능 우선순위, 서비스 플로우 재설계, 메인 시안 3종 · 분석 보고서, 신청자 · 관리자 화면, 공통 필터 · 컴포넌트 규칙 (상용 UI 키트 기반)

**SAP ERP의 불편을 현장 인터뷰로 풀어, 피복관리 SaaS를 새로 기획했습니다**

코레일의 피복 신청과 관리를 SAP ERP에서 새 SaaS 플랫폼으로 옮기는 프로젝트에서 PM을 맡았습니다. 현장 인터뷰로 페인포인트와 기능 우선순위를 정하고, 전체 화면 기획과 UI/UX, 서비스 플로우를 다시 설계했습니다.

### Brief — 매일 쓰는 업무 시스템은 화려함보다 바로 일할 수 있어야 합니다

피복 신청과 관리는 SAP ERP 안에서 이뤄지고 있었고, 현장에서는 불편이 쌓여 있었습니다. 새 SaaS 플랫폼을 기획하면서, 현장 인터뷰로 무엇이 불편한지부터 찾고 기능의 우선순위를 정했습니다.

### State 1. Discovery — 현장 인터뷰로 페인포인트와 우선순위를 찾았습니다

현장 인터뷰로 페인포인트를 발굴하고 기능 우선순위를 정의했습니다.

SAP ERP의 불편사항을 개선하기 위해 신규 SaaS 플랫폼을 기획하고 프로젝트 전체를 관리했습니다. 현장 인터뷰로 페인포인트를 발굴해 기능 우선순위를 정의했고, 업무 프로세스에 맞춰 서비스 플로우를 다시 설계했습니다.
정기 리뷰 미팅을 진행하며 피드백을 관리하고, 개발팀에 요구사항을 전달하는 클라이언트 커뮤니케이션을 총괄했습니다.

화면: 신청자 메인 시안 — 전체 품목 리스트 열고 닫기, 로그인, 신청자 — 마이페이지

### State 2. Direction — 세 가지 시안 중 ‘바로 일할 수 있는’ 쪽을 추천했습니다

메인 화면 시안 3종을 비교한 분석 보고서로 시안 3을 추천했습니다.

메인 화면은 세 방향으로 시안을 만들고, 장점과 사용성 한계를 비교한 분석 보고서로 클라이언트에 보고했습니다. 아래는 그 보고서입니다.
보고서 — 코레일 피복관리 시스템 디자인 시안 분석 보고서: 시안 1과 2는 브랜드와 감성을 잘 드러내지만, 매일 쓰는 업무 시스템에서는 장식이 정보 전달과 업무 속도를 떨어뜨립니다. 공지와 포인트 현황, 신청 품목을 중요도 순서로 배치한 시안 3을 추천합니다.
시안 1 자연 풍경 배경 — 특징: 푸른 산과 들판을 배경으로 한 흰색 기차 이미지, 대형 히어로 섹션으로 시각적 임팩트 강조, 포인트 시스템과 5개 주요 메뉴를 카드 형태로 하단 배치. 장점: 강한 브랜드 아이덴티티와 코레일의 정체성 표현, 첫 방문 사용자에게 친근하고 신뢰감 있는 인상, 시각적으로 매력적이고 기억에 남는 디자인. 한계: 과도한 시각 요소로 정보 전달력 저하, 실무진의 빠른 업무 처리에는 비효율적, 메뉴 접근성이 상대적으로 떨어짐.
시안 2 지하철역 일러스트 — 특징: 따뜻한 톤의 지하철역 내부 일러스트, 사람들의 모습으로 휴먼 터치 강조, 같은 메뉴 구성에 더 친근한 분위기. 장점: 사용자 친화적이고 접근하기 쉬운 느낌, 대중교통 이용자에게 친숙한 환경 표현, 감성적인 연결고리. 한계: 업무용 시스템으로는 과도한 장식 요소, 핵심 기능에 대한 집중도 분산 가능성, 로딩 시간과 성능에 영향 우려.
시안 3 심플 기능 중심 (추천) — 특징: 상단 배너로 중요 공지사항을 바로 확인, 포인트 현황과 공지사항을 명확히 나눠 배치, 신청 품목 관리 기능을 하단에 체계적으로 정리. 장점: 업무 효율 — 필요한 정보를 한눈에, 클릭 수를 줄인 내비게이션, 중요도에 따른 정보 위계, 사용자 중심 — 피복신청 기간과 포인트 현황을 먼저 노출, 자주 쓰는 기능의 접근성 향상, 유지보수 — 단순한 구조로 개발과 수정이 쉽고, 반응형에서도 안정적이며, 기능을 더하기 쉬움.
추천 근거: 즉시 업무 가능 — 로그인 후 바로 필요한 정보를 확인합니다. 학습 비용 최소화 — 별도 사용법 교육 없이도 직관적으로 씁니다. 높은 재사용률 — 단순한 구조가 계속 쓰게 만듭니다. 개발 효율 — 빠르게 구현하고 안정적으로 운영할 수 있습니다.
시안 1과 2는 브랜딩 측면에서 우수하지만, 실제 업무 환경에서는 시안 3의 실용적인 접근이 사용자 만족도와 업무 효율을 함께 채울 수 있다고 판단했습니다.

화면: 시안 1 — 자연 풍경 배경, 시안 2 — 지하철역 일러스트, 시안 3 — 심플 기능 중심

### State 3. Admin — 관리자의 품목 관리와 신청 현황

피복 마스터와 신청 현황, 공통 필터와 컴포넌트 규칙을 정의했습니다.

관리자는 피복 마스터에서 품목을 관리하고, 신청 현황을 확인합니다. 상용 UI 키트를 바탕으로 공통 필터와 컴포넌트 규칙을 정의하고, 변경 사항은 버전으로 기록했습니다(0.1.0 — 0.1.4, 2025.08 — 2025.09).

화면: 관리자 — 품목 관리, 관리자 — 신청 현황, 신청자 — 게시판 · 피복 나눔방

**자연어로 묻는 금융 검색. 검색 흐름과 데이터 시각화를 설계했습니다**

### Brief — 질문에서 답까지의 거리를 줄이는 일

자연어로 묻고 AI가 분석한 금융 정보를 찾는 검색엔진이었습니다. 데이터 기반 필터링으로 검색 결과의 가독성을 높이고, AI 금융 분석 데이터를 읽히는 화면으로 바꾸는 것이 과제였습니다.

### State 1. Search — 질문에서 답까지, 검색 흐름을 최적화했습니다

기업 검색 첫 화면부터 분석 결과 대시보드까지의 흐름을 설계했습니다.

기업을 검색하는 첫 화면에서 분석 결과를 보는 대시보드까지, 자연어로 묻고 답을 찾는 흐름을 설계했습니다. 데이터 기반으로 검색 결과를 필터링해 결과의 가독성을 높였습니다.

화면: 엔진 — 기업 검색 (첫 화면), 리포트 — 기사 상세

화면: 리포트 — 대시보드, 리포트, 타임라인 애니메이션, 캘린더
